# `torch.compile`: `ForSequenceClassificationLoss` mutates `config.problem_type` on the first call, so the second training step always recompiles

### System info

- transformers: `5.24.0.dev0` (main, git `b7fe69cb19`)
- torch: `2.16.0a0+git57f02f8` (source build)
- Python 3.15, Linux; checked on CPU and on CUDA (B200)

### Description

When `config.problem_type` is `None` (the default for most checkpoints), the classification loss infers it
and **writes it back to the config** (`transformers/loss/loss_utils.py`, `ForSequenceClassificationLoss`):

```python
if config.problem_type is None:
    if num_labels == 1:
        config.problem_type = "regression"
    elif num_labels > 1 and (labels.dtype in (torch.long, torch.int)):
        config.problem_type = "single_label_classification"
    else:
        config.problem_type = "multi_label_classification"
```

Dynamo guards on `config.problem_type is None` for the first compiled graph. After step 0 the config has
changed, the guard fails, and step 1 recompiles, with any input shape (this is not a dynamic-shape
issue). Every `*ForSequenceClassification` / `*ForImageClassification` model trained with
`problem_type` unset pays one extra compile, and with `fullgraph` / `mark_static` setups the recompile
can be surprising.

### Reproduction

`issues/hf/repros/problem_type_config_mutation.py` (`ViTForImageClassification`, 2 layers, train, same
input every step):

```
problem_type before: None
step 0: problem_type='single_label_classification' compiled graphs so far=1
step 1: problem_type='single_label_classification' compiled graphs so far=2
step 2: problem_type='single_label_classification' compiled graphs so far=2
```

### Possible fix

Infer the problem type into a local variable and don't mutate `config` inside the loss (or set it once at
model init / in `from_pretrained` when `num_labels` is known).

### Affected

All sequence / image classification heads that use `ForSequenceClassificationLoss` with
`problem_type=None` (seen: vit).
