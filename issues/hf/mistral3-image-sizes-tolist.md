# `torch.compile`: Mistral3 / Pixtral derive split sizes from `image_sizes` with `.tolist()` and loop per image in Python

### System info

- transformers: `5.24.0.dev0` (main, git `b7fe69cb19`)
- torch: `2.16.0a0+git57f02f8` (source build)
- Python 3.15, Linux; checked on CPU and on CUDA (B200)

### Description

`Mistral3Model.get_image_features` (`modeling_mistral3.py:239`):

```python
downsample_ratio = self.vision_tower.patch_size * self.config.spatial_merge_size
split_sizes = (
    (torch.as_tensor(image_sizes, device=image_features.device) // downsample_ratio).prod(dim=-1).tolist()
)
```

the patch merger loops over `image_features.split(tokens_per_image)` (`:86`), and the Pixtral vision
model slices each image's patch embeddings with sizes read from `image_sizes` (`modeling_pixtral.py:418`):

```python
patch_embeds_list = [
    embed[..., : (size[0] // self.patch_size), : (size[1] // self.patch_size)]
    for embed, size in zip(patch_embeds, image_sizes)
]
```

All of these turn tensor values into Python ints -> graph breaks, plus a follow-on break inside the
comprehension ("Failed to handle graph break gracefully").

Numbers are from the graph-break harness: model built from its config with random weights and reduced layers, one `torch._dynamo.explain` call per scenario. mistral3: 14 graphs / 13 breaks (CPU), 13 / 12 (CUDA) in every scenario. With
`capture_scalar_outputs` + `capture_dynamic_output_shape_ops`: 9 graphs; the rest are data-dependent
guards in the patch merger.

### Possible fix

`image_sizes` comes from the processor; accepting it as a Python list (and not converting it to a tensor
in the processor / generate path) would remove most of these. Otherwise, compute split sizes once and pass
them down instead of re-deriving them in three places.

### Affected

mistral3, pixtral (vision tower). Similar: `llava-next-anyres-image-size-tolist`,
`apertus1p5-image-sizes-tolist`.
