# `torch.compile`: ZONOS3-Mini MoE layers graph-break on `torch.unique(choices).tolist()` + `nonzero()` (17 breaks per LM step)

### System info

- Model repo: `Zyphra/ZONOS3-Mini-hf`, revision `e39d30d` (`trust_remote_code=True`)
- transformers: `5.24.0.dev0` (git `b7fe69cb19`)
- torch: `2.16.0a0+git57f02f8` (source build)
- Python 3.15, Linux; checked on CPU and on CUDA (B200)

### Description

`Zonos3MiniLM._feed_forward` (`modeling_zonos3.py:313`) dispatches tokens to the routed experts with a
Python loop over the experts that were actually chosen:

```python
choices = torch.topk(logits.float() - bias, c["moe_topk"], -1).indices
weights = logits.float().gather(-1, choices).softmax(-1)
latent = F.linear(x, f.latent_down.weight)
...
for expert in torch.unique(choices).tolist():                 # :321
    token, rank = (choices == expert).nonzero(as_tuple=True)    # :322
    gate_up = F.linear(latent[token], f.experts.gate_up_proj[expert])
    ...
```

`torch.unique` has a data-dependent output shape (`Dynamic shape operator`), `.tolist()` is a host sync
(`Data dependent operator`), and Dynamo can't resume inside the loop ("Failed to handle graph break
gracefully"), so each MoE layer splits the graph and part of it runs eagerly.

With the LM reduced to 4 layers (3 MoE layers), one `forward` step (`input_ids` of 32 prompt rows):

| | CPU | CUDA (B200) |
|---|---|---|
| static (`torch._dynamo.explain`) | 18 graphs / 17 breaks | 18 / 17 |
| `torch.compile(dynamic=True)` + Inductor, 32 / 40 / 56 rows | 25 graphs, 0 recompiles | 25, 0 |

All breaks are at `modeling_zonos3.py:321-322`. The full 11-layer model has 10 MoE layers, so more.

### Reproduction

`issues/hf/repros/zonos3_moe_unique_expert_loop.py` (the routing code copied from `_feed_forward`, small
sizes):

```
[unique().tolist() + nonzero] graphs=1 breaks=0
    - Dynamic shape operator
    break reasons recorded: 1          (Dynamo skips the whole function -> runs eagerly)
[static expert loop + mask]   graphs=1 breaks=0
    break reasons recorded: 0
outputs match
```

### Possible fix

- Loop over all experts statically (`for expert in range(n_experts)`) with a per-token routing weight
  (`(weights * (choices == expert)).sum(-1)`, zero for tokens not routed to that expert). Same output
  (checked in the repro) and a single graph, but it computes every expert on every token: fine for short
  prompts and decode steps, wasteful for long prefills.
- Or use a sort-based dispatch with `torch._grouped_mm` (no host sync, no wasted FLOPs), as the
  transformers MoE integrations do.

### Notes

- `forward` is decorated `@torch.no_grad()` and takes batch size 1 only, so only the eval / inference
  path applies.
- The KV / GDN cache (`Zonos3MiniCache`) is a Python object mutated in place inside `forward`; with this
  harness it did not cause extra breaks (all breaks are at `:321-322`). Not checked: how it affects guards
  and recompiles across real decode steps, where the cache grows.

### Affected

zonos3_mini (`Zyphra/ZONOS3-Mini-hf`), eval on CPU and CUDA, static and dynamic shapes.
