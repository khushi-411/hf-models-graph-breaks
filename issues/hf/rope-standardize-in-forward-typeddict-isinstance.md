# `torch.compile`: LongRoPE update calls `config.standardize_rope_params()` inside forward; validating `config.rope_parameters` hits `isinstance(dict, RopeParameters)` (a TypedDict) -> graph break

### System info

- transformers: `5.24.0.dev0` (main, git `b7fe69cb19`)
- huggingface_hub: `2.4.0`
- torch: `2.16.0a0+git57f02f8` (source build)
- Python 3.15, Linux; seen on CPU and CUDA (B200)

### Description

For LongRoPE models (PhiMoE, `microsoft/Phi-3.5-MoE-instruct` config), the rotary embedding's
`@dynamic_rope_update` wrapper (`modeling_rope_utils.py:129`) calls `longrope_frequency_update`. The first
time it runs, `long_inv_freq` doesn't exist yet, so it computes it **inside forward**
(`modeling_rope_utils.py:64`):

```python
long_inv_freq = getattr(self, f"{prefix}long_inv_freq", None)
if long_inv_freq is None:
    rope_init_fn = ROPE_INIT_FUNCTIONS[rope_type]
    long_inv_freq, _ = rope_init_fn(self.config, device, seq_len=original_max_position_embeddings + 1, ...)
```

The init function (`_compute_longrope_parameters`) starts with

```python
# For backward compatibility standardize the `rope_parameters_dict` if it uses old format
config.standardize_rope_params()          # modeling_rope_utils.py:543
```

which ends with `self.rope_parameters = rope_parameters`, i.e. it **mutates the config during forward**.
That assignment is validated by huggingface_hub's strict dataclasses, which check the value against the
field type, including `isinstance(value, RopeParameters)`; `RopeParameters` is a `TypedDict`
(`modeling_rope_utils.py:679`), for which `isinstance` raises `TypeError`. Eager mode copes, but Dynamo
can't trace this and graph-breaks:

```
Graph break in user code at huggingface_hub/dataclasses.py:626
builtin isinstance() with classinfo that does not support issubclass()
  Explanation: issubclass(<class 'dict'>, <class 'transformers.modeling_rope_utils.RopeParameters'>) raised TypeError:
  TypedDict does not support instance and class checks.
  Developer debug context: isinstance(ConstDictVariable(), <class 'transformers.modeling_rope_utils.RopeParameters'>)
  (gb1583)
```

It shows up with `torch.compile(model, dynamic=True)` for phimoe eval and train (CPU and CUDA), in
addition to the two data-dependent LongRoPE branches tracked in `phimoe-longrope-seq-len-branch`.

### Reproduction

`issues/hf/repros/rope_standardize_typeddict_isinstance.py` (real `PhimoeRotaryEmbedding` with the
`microsoft/Phi-3.5-MoE-instruct` config, `config.json` only), run with `TORCH_LOGS=graph_breaks`:

```
rope_type: longrope
[rotary embedding, static] graphs=4 breaks=3     (the known LongRoPE data-dependent branches)
[rotary embedding, dynamic=True] compiled graphs: 5
...
Graph break in user code at .../huggingface_hub/dataclasses.py:626
builtin isinstance() with classinfo that does not support issubclass()   (x2, frames 3 and 4)
```

### Possible fix

- transformers: standardize `rope_parameters` once (at config init / load) and don't call
  `config.standardize_rope_params()` from the rope init functions at forward time; or compute
  `long_inv_freq` in `__init__` (it only depends on the config), so forward never builds it.
- PyTorch (Dynamo) side: when emulating `isinstance(x, cls)` raises `TypeError` in Python, Dynamo could
  raise the same `TypeError` inside the traced code (so the caller's `try/except` works) instead of graph
  breaking.

### Affected

phimoe (eval_forward, train_forward with dynamic shapes); likely other LongRoPE models that go through
`longrope_frequency_update` (e.g. phi3 with LongRoPE checkpoints; not checked). Related: `phimoe-longrope-seq-len-branch`,
`dynamic-rope-data-dependent`.
