# MoE `transformers::grouped_mm_fallback` custom op syncs to the CPU (`offs.tolist()`) but isn't tagged `cudagraph_unsafe`: `mode="reduce-overhead"` crashes during capture

### System info

- transformers: `5.24.0.dev0` (main, git `046bdb8cc2`)
- torch: `2.16.0a0+gitf29b6d5`, CUDA 13.2, NVIDIA B300

### Description

`torch.compile(model, mode="reduce-overhead")` on an fp32 MoE model fails while recording the CUDA graph:

```
torch/_inductor/cudagraph_trees.py:1572 _record -> partition_0
  -> transformers/integrations/moe.py:206 _grouped_mm_fallback
RuntimeError: Cannot copy between CPU and CUDA tensors during CUDA graph capture unless the CPU tensor is pinned.
```

`_grouped_mm_fallback` (and `_grouped_mm_fallback_bwd`) loop over `offs.tolist()`, a device-to-host copy, which can't
be captured. They're registered with `torch.library.custom_op(...)` without tags, so Inductor treats them as
cudagraph-safe and captures them into the graph.

Seen in `inkling2`, `inkling2_vlm`, `inkling2_mini`, `inkling2_mini_vlm` train with `mode="reduce-overhead"` (fp32
models, so the grouped-mm fallback is used). Eval hits it too: by default eval fails earlier on
`inductor-merge-loops-minmax-not-comparable`, and with that fix applied (`GB_PATCH=identity`) eval and train both
fail here, in all four models, including the full-depth configs. Check: `python -m graph_breaks.modes --model inkling2 --mode cudagraphs --device cuda`.

### Possible fix

Register both ops with `tags=(torch.Tag.cudagraph_unsafe,)`. Inductor then partitions the graph around them
(`graph_partition`) or skips cudagraphs for that graph with a logged reason, instead of crashing.
