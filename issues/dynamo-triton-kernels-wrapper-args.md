# Dynamo: Triton kernels launched with `triton_kernels` wrapper objects graph-break about 10 times per MoE layer

### System info

- torch: `2.16.0a0+git57f02f8` (source build, CUDA 12.8)
- transformers: `5.24.0.dev0` (main, git `046bdb8cc2`)
- Python 3.15, Linux; CUDA results on H100 (sm_90)
- triton 3.9.0, kernels 0.18.2 (kernels-community/gpt-oss-triton-kernels)

### Description

transformers' MXFP4 experts (gpt-oss) run the `triton_kernels` MoE path (`routing`, `topk`, `matmul_ogs`).
Those kernels take `triton_kernels.tensor.Tensor` / `Storage` wrapper objects as arguments. Dynamo's
Triton-kernel support rejects them:

```
Encountered triton kernel unsupported feature: Unexpected argument type for a Triton kernel:
UserDefinedObjectVariable(Tensor)     (topk.py:41)
```

Dynamo then tries to trace Triton's own launcher, and each of these steps breaks again:

- `JITFunction.run` / `parse_options`
- `native_specialize_impl`
- `CudaLauncher.__init__`
- `CudaDriver.get_current_target`
- `Storage.is_tma_compliant`

openai/gpt-oss-20b (real MXFP4 checkpoint, 2 layers): **20 graphs / 19 breaks** in eval, 21 / 20 in train.
That is all from the expert path; the unquantized `gpt_oss` entry compiles with fewer breaks.

### Reproduction

`python -m graph_breaks.check --model gpt_oss_mxfp4 --device cuda` (torch-dev-quant env).

### Possible fix

Unwrap `triton_kernels` Tensor/Storage dataclasses into their underlying `torch.Tensor` + metadata when
binding user Triton kernel arguments, or have the kernels expose a `torch.library` custom op that Dynamo can
treat as opaque.
