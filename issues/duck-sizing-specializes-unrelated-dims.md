# [dynamic shapes] Duck sizing merges batch with `num_kv_heads` in KV-cache decode; a constant head count then specializes the batch, so `generate()` recompiles for every new batch size

### System info

- torch: `2.16.0a0+git57f02f8` (CPU), `2.16.0a0+gitf29b6d5` (CUDA, B300)
- transformers: `5.24.0.dev0` (main, git `046bdb8cc2`)

### Description

With `torch.compile(model.forward, dynamic=True)` and `model.generate()` (DynamicCache), the decode graphs are
compiled with the batch size fixed whenever the first batch size happens to equal the number of KV heads.
Every later batch size then recompiles the decode graphs.

The KV cache is a graph input of shape `(batch, kv_heads, seq, head_dim)`. With batch == kv_heads == 2, duck
sizing gives both dims one symbol `s0`. The new keys are built with `kv_heads` as a Python int from the config,
and `torch.cat([cache.keys, key_states], dim=-2)` (`transformers/cache_utils.py:242`) needs the head dims to match,
so `s0 == 2` and the **batch** becomes 2 as well. The guard that later fails:

```
- 0/1: tensor 'kwargs['input_ids']' size mismatch at index 0. expected 2, actual 3
```

Repro (pure torch, CPU, ~20 lines): [`issues/repros/duck_sizing_kv_cache_batch_heads.py`](repros/duck_sizing_kv_cache_batch_heads.py)

```
first batch == kv_heads, duck sizing  : 2 graphs for 3 batch sizes
first batch != kv_heads, duck sizing  : 1 graphs
first batch == kv_heads, no duck shape: 1 graphs
```

Model-level (inkling2, 2 KV heads, `generate()` with 8 new tokens):

| first batch | `use_duck_shape` | graphs on 1st call | 2nd call (batch 3) | 3rd call (batch 5) |
|---|---|---|---|---|
| 2 | True (default) | 3 | **2** | 0 |
| 3 | True | 3 | 0 | – |
| 2 | False | 3 | 0 | – |

Batch == number of KV heads is easy to hit (GQA models commonly have 2, 4 or 8 KV heads, and those are also
common batch sizes). Batch 1 is specialized anyway (0/1 specialization), so this shows up at batch 2+. Any other
config constant that equals the batch (or another input dim) on the first call can do the same. Seen in all five Inkling models
(`python -m graph_breaks.modes --model inkling2 --mode generate_dynamic`).

### Possible fix

- When a duck-sized symbol gets specialized to a constant because it was unified with a literal, check
  whether the other dims sharing the symbol could be split off instead of all being specialized (i.e. only the
  dim that met the constant becomes static), or
- don't duck-size dims of the same input tensor against each other, or
- document it in the dynamic-shapes guide with the workaround (`torch.fx.experimental._config.use_duck_shape =
  False`, or `torch._dynamo.mark_dynamic(cache.keys, 0)`), and have transformers apply it for its cache tensors.
