# `torch._grouped_mm` (bf16) on B300 crashes with `CUDA error: unspecified launch failure` when PyTorch is built with `TORCH_CUDA_ARCH_LIST=10.3` (no `a`)

### System info

- torch: `2.16.0a0+gitf29b6d5` (source build, CUDA 13.2, `TORCH_CUDA_ARCH_LIST=10.3`, `torch.cuda.get_arch_list() == ['sm_103']`)
- GPU: NVIDIA B300 SXM6 (sm_103)
- Linux, Python 3.15

### Description

bf16 `torch._grouped_mm` launches the CUTLASS sm100 kernel, which needs arch-specific instructions (TMA, TMEM,
tcgen05) that are only compiled for `10.0a` / `10.3a` targets. In a build for plain `10.3` those code paths are
compiled out, CUTLASS prints

```
Trying to use tma without CUTE_ARCH_TMA_SM90_ENABLED.
Attempting to use TMEM allocation PTX without CUTE_ARCH_TCGEN05_TMEM_ENABLED
```

from the device, and the kernel faults:

```
torch.AcceleratorError: CUDA error: unspecified launch failure
```

The CUDA context is then unusable, so the process has to be restarted. fp32 `_grouped_mm` (fallback path) works.

Repro (B300, this build), [`issues/repros/grouped_mm_sm103.py`](repros/grouped_mm_sm103.py):

```python
G, M, K, N = 4, 64, 128, 256
a = torch.randn(M * G, K, device="cuda", dtype=torch.bfloat16)
b = torch.randn(G, K, N, device="cuda", dtype=torch.bfloat16)
offs = torch.arange(M, M * G + 1, M, device="cuda", dtype=torch.int32)
torch._grouped_mm(a, b.transpose(-2, -1).contiguous().transpose(-2, -1), offs=offs)
torch.cuda.synchronize()   # float32: ok · bfloat16: unspecified launch failure
```

Every bf16 MoE model in transformers that uses `experts_implementation="grouped_mm"` (the default when
available) crashes in eager on such a build, so it looks like a model or compile bug: here `inkling` eval/train
on CUDA, and likely the MoE "unspecified launch failure" runs on B300 in the earlier unbacked sweep
(deepseek_v2/v3/v32, dots3_note, ernie4_5_moe, glm4_moe, granitemoe).

### Cause

`GroupedBlas.cpp` picks `GroupedMMKernel::Cutlass` when `scaled_mm_arch_allowed(sm90_only, sm100_only)` is true.
That check (`ScaledBlasDeviceUtils.cpp`) only looks at the **device** (`dprops->major == 10`), not at whether
the binary contains an arch-specific (`sm_100a` / `sm_103a`) build of the kernel.

### Possible fix

- Gate the CUTLASS path on what was compiled, e.g. a host-side flag set from the build's arch list (or a
  device-side probe of `__CUDA_ARCH_FEAT_SM100_ALL` / `__CUDA_ARCH_FEAT_SM103_ALL`), and use
  `_grouped_mm_fallback` otherwise, or
- `TORCH_CHECK` with a clear message ("rebuild with TORCH_CUDA_ARCH_LIST=10.3a") instead of launching, and
- warn at build time when `10.x` is in `TORCH_CUDA_ARCH_LIST` without the `a` suffix while the grouped / scaled
  GEMM kernels are enabled.

Local workaround: rebuild with `TORCH_CUDA_ARCH_LIST="10.0a;10.3a"`, or run MoE models with
`model.set_experts_implementation("eager")` (this repo: `GB_EXPERTS_IMPL=eager`).
