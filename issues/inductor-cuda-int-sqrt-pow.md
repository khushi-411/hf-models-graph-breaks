# Inductor (CUDA): `int(s ** 0.5)` on a dynamic size is off by one for some perfect squares

### System info

- torch: `2.16.0a0+git57f02f8` (source build, CUDA 12.8)
- transformers: `5.24.0.dev0` (main, git `046bdb8cc2`)
- Python 3.15, Linux; CUDA results on H100 (sm_90)

### Description

With `dynamic=True`, `int(x.shape[0] ** 0.5)` is lowered to
`trunc(libdevice.pow(float(s), 0.5))` in the Triton kernel. CUDA's `pow` is not exact for a 0.5 exponent:
`pow(9.0, 0.5)` comes out just below 3, so `trunc` gives 2. CPU (C++ `std::pow`) is exact.

The result is a wrong integer, not a compile error. Anything derived from it is silently wrong unless something
downstream asserts.

### Reproduction

`issues/repros/inductor_cuda_int_sqrt_pow.py`:

```python
def f(x):
    return torch.full((1,), int(x.shape[0] ** 0.5), device=x.device)
g = torch.compile(f, dynamic=True)
# check g(torch.empty(n * n)) == n for n in 2..199
```

```
cpu wrong for perfect squares: [] (0 of 198)
cuda wrong for perfect squares: [9, 7056, 7396, 9025, 13689, 21609, 24964] (7 of 198)
```

### Where it shows up

Gemma 4 vision pooler (`Gemma4VisionPooler._avg_pool_by_positions`):

```python
k = int((input_seq_len // length) ** 0.5)          # 36 patches / 4 tokens -> k = 3, compiled CUDA gives 2
kernel_idxs = torch.div(clamped_positions, k, rounding_mode="floor")
weights = F.one_hot(kernel_idxs.long(), length).float() / k_squared
```

With `k = 2` the pooling indices go past `length` and `F.one_hot`'s device-side assert fires
(`one_hot: Class values must be smaller than num_classes.`). gemma4, gemma4_moe and gemma4_e4b all crash with
`dynamic=True` on CUDA; static compile and CPU are fine. `issues/repros/gemma4_vision_pool_sqrt_k.py` narrows
it to the `k` step (`v_k: eager=[3] compiled=[2]`; a literal divisor is fine).

### Possible fix

Lower `x ** 0.5` to `sqrt` (correctly rounded, so exact for perfect squares), or compute integer powers of
SymInts with integer arithmetic (`IntTrueDiv`/`isqrt`-style) instead of going through float `pow`.
